## 1. Опис сервісу
Для моделювання обрано REST API сервіс управління кулінарними рецептами **RecipeBookApi** (.NET 8), розроблений у межах курсового проєкту. Сервіс дозволяє користувачам (кулінарам, домашнім кухарям та клієнтським веб/мобільним додаткам) створювати, переглядати, оновлювати та видаляти рецепти зі списком інгредієнтів, а також перевіряти стан доступності системи (`/health`).

## 3. Опис архітектурного дизайну

1. **Сервіс та Namespace:** У межах Kubernetes-кластера (що працює на Worker Node-ах) моделюється сервіс `RecipeBookApi`, ізольований в окремому продакшн-просторі імен (`Namespace`) **`recipebook-prod`**.
2. **Маршрутизація зовнішнього трафіку:** Запити користувачів надходять на домен **`api.recipebook.local`**, через DNS резолвляться на зовнішній **Load Balancer**, після чого потрапляють на **Ingress Controller**. Ingress аналізує заголовок `Host` (`api.recipebook.local`) та шлях (`Path`: `/recipes`, `/health`) і маршрутизує трафік на внутрішній **Service** **`recipebook-svc`** типу `ClusterIP` (порт `80 → 8080`), який балансує навантаження між активними Pod-ами.
3. **Кількість Pod-ів та відмовостійкість:** У конфігурації `Deployment` (`recipebook-api`) закладено **3 репліки (3 Pod-и)**, у кожному з яких запущено контейнер із образом `ghcr.io/deiv228/recipebookapi-api:1.0.0`. Така кількість забезпечує високу доступність, балансування навантаження та безперебійну роботу сервісу під час оновлення (Rolling Update) або збою одного з вузлів.
4. **Ланцюжок доставки коду (Git → CI/CD → Registry → Cluster):** Вихідний код зберігається в GitHub-репозиторії `github.com/Deiv228/RecipeBookApi`. Після кожного `git push` запускається пайплайн **GitHub Actions (CI/CD)**, який виконує тестування, збирає Docker-образ і публікує його в **GitHub Container Registry (GHCR)** під тегом `ghcr.io/deiv228/recipebookapi-api:1.0.0`, звідки Kubernetes `Deployment` автоматично викачує образ при створенні або оновленні Pod-ів.
